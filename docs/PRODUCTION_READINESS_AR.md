# مراجعة جاهزية SpeedInfer للإنتاج

تاريخ المراجعة: 2026-09-27. نطاق العمل: نسخة المشروع المحلية، اختبارات معزولة، وفحص HTML الصفحة المنشورة دون تغييرها.

## القرار

**النسخة ليست معتمدة كإنتاج كامل بعد.** تم إصلاح مخاطر حقيقية في بوابة الاستدلال والمحاسبة والوثائق؛ لا يوجد في هذه المراجعة GPU متصل أو اختبار حمل GPU أو تدقيق أمني مستقل. إضافة GPU وحدها لا تفعّل التدريب والنشر الموجودين في مساحة العمل: تلك المسارات ما زالت محاكاة وتحتاج عامل تنفيذ وتكامل تخزين وجدولة.

مرجع المستخدم الحالي هو `/guide`، والمرجع التفاعلي `/docs`. تقارير الاختبارات والخطط الأقدم توثق وقتها ولا تعد إثباتًا لجاهزية النسخة الحالية.

## ما تم إصلاحه

- منع الردود المصطنعة عند تعطل العامل خارج بيئة الاختبار؛ يعاد 503 ولا تحسب تكلفة استدلال.
- طلبات المحادثة والإكمال تتحقق من الصلاحيات، ويُرفض نفاد الرصيد قبل الاتصال بالعامل.
- حجز دائم للرصيد في قاعدة البيانات قبل التشغيل، وتسوية التكلفة والسجل في معاملة واحدة؛ لا تعتمد حقيقة الرصيد على بقاء Redis أو كتابة رصيد قديم من طلب متزامن.
- تسوية مرة واحدة بمعرّف يولده الخادم؛ إعادة العامل لنفس معرّف الرد لا تتسبب في تضارب سجل المحاسبة.
- تحديثات المدفوعات والإحالات تزيد الرصيد بتعبيرات قاعدة البيانات بدل استبداله بنسخة قديمة.
- استخدام استهلاك البث الصادر من العامل، وإلغاء تقدير `max_tokens / 4` ورقم TTFT الثابت. وقت أول محتوى يقاس محليًا، ولا يمثل قياسًا داخل GPU.
- عند نقص بيانات الاستهلاك أو انقطاع البث: حدث خطأ SSE وإرجاع الحجز، دون نجاح وهمي. إذا فشلت العملية قبل إرسال الترويسات يعود خطأ HTTP.
- فصل `/health` لحيوية البوابة عن `/ready` الذي يفحص DB وRedis ووجود النموذج المطلوب في كتالوج العامل. لا يثبت `/ready` سرعة أو دقة الاستدلال؛ يلزمه اختبار توليد حقيقي.
- Redis يفشل مغلقًا خارج الاختبارات بدل استبداله بذاكرة عملية منفردة.
- تقييد المدخلات والمخرجات، `n=1`، ورفض الخيارات غير المدعومة. الإكمال القديم يدعم نصًا واحدًا دون بث؛ البث في محادثة النص فقط.
- تمرير `VLLM_API_KEY` للعامل من إعدادات الخادم، دون كشفه للمستخدم.
- حظر مفاتيح الاختبار المعروفة حتى إن بقيت سجلات قديمة لها في قاعدة إنتاج.
- السماح بمحاولة تعافٍ بعد توقف مؤقت للعامل؛ تدوير الطلبات بين عمال نفس النموذج. لا تبديل صامت إلى نموذج مختلف.
- منع بدء الإنتاج قبل ترحيل قاعدة البيانات إلى `0007_inference_reservations`.
- إصلاح أمثلة الموقع لتستخدم `https://speedinfer.com/v1` ونموذجًا من الكتالوج، وحذف معاملات TensorRT/FP8 غير المطبقة.
- إزالة وعود سرعة أقل من 100ms وZero Data Retention وSLA وعتاد لم يتم إثباتها.
- صورة Open Graph/Twitter بهوية SpeedInfer، وأيقونة لمس، وتحسينات تركيز لوحة المفاتيح والحركة المخفضة ومسافات السياسات وإشعار واضح بحالة المعاينة.
- إصلاح بناء Docker ليشمل حزمة التطبيق وقت تثبيت الاعتمادات، وإضافة Alembic وبرنامج تشغيل PostgreSQL. إعداد Compose يتطلب أسرارًا صريحة وصورة vLLM محددة، وتقتصر منافذ خدماته على localhost.
- إعداد Nginx المقترح يسمح برفع 20MiB لمسار الملفات ويعطل تجميع استجابة البث. يجب دمج التغييرات مع TLS الفعلي، لا استبدال إعداد الإنتاج بلا مراجعة.

## كيف تعمل المحاسبة الجديدة

الحجز = سقف سياق الإدخال المهيأ × سعر الإدخال + `max_tokens` × سعر الإخراج، مقسومًا على مليون. هذا سقف تحفظي، وليس عدد توكنز فعليًا ولا مبلغ فاتورة نهائية. يحتاج الحساب إلى رصيد متاح يغطيه؛ التزامن يستلزم تغطية مجموع الحجوزات. يتقدم الرصيد التجريبي في الخصم ثم المدفوع، ويرجع المتبقي إلى مصدره.

عند نجاح الطلب تحسب التكلفة من `usage` المرسلة من العامل. إذا تجاوزت تكلفة العامل الحجز يرفض الرد وتحرر التكلفة بدل أخذ رصيد غير مصرح به. لا يفرض النظام رسومًا على رد غير مكتمل أو غير قابل للمحاسبة. هذا الاختيار يحمي المستخدم لكنه قد يحمّل المشغل تكلفة حوسبة ملغاة؛ يلزم مراقبة إساءة قطع الاتصالات.

عند موت العملية فجأة تبقى الحجوزات محفوظة. أوقف العملية المعنية، تحقق من الطلب، ثم استخدم `python scripts/reconcile_inference_holds.py` للعرض، و`--release ID --gateway-stopped` لتحرير حجز محدد أقدم من 15 دقيقة. لا تحرر حجوزات عمال أخرى لا تزال تنفذ. لا يوجد عامل تسوية تلقائي بعد.

الأسعار والأرصدة تستخدم Float في المخطط الحالي. قبل حمل مالي واسع يلزم اعتماد تمثيل عشري/وحدات نقدية صحيحة وترحيل مالي مستقل. SQLite ليس إثبات تحمل عالي؛ اختبارات PostgreSQL الفعلية مطلوبة للانتقال متعدد العمال.

## تشغيل GPU للمرة الأولى

1. اختر صورة vLLM مختبرة ومثبتة وGPU يناسب حجم الأوزان والسياق، والتزم بترخيص النموذج. لا تفعّل تنفيذ كود نموذج خارجي دون مراجعة.
2. شغّل العامل باسم served model يطابق `DEFAULT_MODEL`. اجعله داخل شبكة خاصة ومحمياً بـAPI key. `VLLM_BASE_URL` هو جذر الخادم بدون `/v1`، واضبط `VLLM_API_KEY` ووقت الانتظار وسقف السياق والأسعار.
3. خذ نسخة احتياطية قابلة للاستعادة، ثبّت الاعتمادات، ونفذ `python -m alembic upgrade head` قبل إعادة تشغيل البوابة. لا تستخدم `stamp` لإخفاء اختلاف المخطط. الترحيل الجديد يأتي بعد `0006_dual_balance`.
4. حافظ على `/etc/speedinfer/speedinfer.env` وبيانات الإنتاج واستثناءاتهما من الرفع. لا تطبع الأسرار في سجلات العمل.
5. افحص `/health` ثم `/ready`، وأنشئ مفتاح تقييم مخصصًا برصيد مضبوط. لا تستخدم مفاتيح الاختبار العامة.
6. شغّل `scripts/test_inference.py` مع `SPEEDINFER_API_KEY` واسم النموذج الحقيقي، وتحقق من الردين العادي والبث والأرصدة. هذه الطلبات مدفوعة حسب الاستخدام.
7. اختبر مفتاحًا بلا رصيد، مفتاحًا ملغيًا، حد الطلبات، فصل العامل، انقطاع Redis، قطع بث المستخدم، وإعادة تشغيل البوابة أثناء حجز نشط. تحقق من السجل والتسوية.
8. نفذ قياس حمل على GPU الفعلي: طراز GPU/VRAM، النموذج وإصداره، precision، طول prompt/output، معدل التزامن، warmup، P50/P95/P99 TTFT وزمن الرد، توكنز/ثانية، أخطاء، OOM. خزّن القياسات الخام. لا تستبدلها بأرقام جودة النماذج العامة أو نتائج العامل الاختباري.
9. اختبر استعادة النسخ الاحتياطية، TLS، حدود جسم الطلب، وصول الأسرار، الجدار الناري، تنبيهات 5xx/429 والتسويات العالقة، وسياسة السجلات والاحتفاظ.

## المستندات التجارية

حسب توجيه المؤسس: رصيد التوكنز المدفوع غير قابل للاسترداد كقاعدة عامة، مع بقاء الحقوق الإلزامية ومتطلبات مزود الدفع. الطلاب والباحثون يمكنهم طلب مراجعة استرداد لتدريب/ضبط دقيق مدفوع حدث به خلل، دون وعد قبول تلقائي. المحاكاة مجانية فلا يوجد مبلغ تدريب يسترد منها.

لا تعني سياسة تشغيلية مكتوبة اعتمادًا قانونيًا. **SpeedInfer.com اسم خدمة وليس إثباتًا لشخصية قانونية**. ما زال يلزم اسم الكيان المسجل وبلد التسجيل وعنوانه، الاختصاص القانوني، بيانات الفوترة والضرائب، مدد الاحتفاظ والحذف والنسخ الاحتياطية، قائمة المعالجين والمناطق، وأدوار ومسؤوليات اتفاقية معالجة البيانات. يلزم مراجعة متخصصة قبل تعاقد شركات أو معالجة بيانات منظمة. لا توجد شهادة SOC 2/ISO أو عضوية NVIDIA مثبتة بهذه المراجعة.

## النشر

الإصلاحات محلية. آخر محاولة SSH موثقة رُفضت بالمفتاح المتاح؛ لا يوجد دليل نشر لهذه المراجعة. صورة المشاركة الجديدة تحتاج رفعًا ثم إعادة جلب معاينة الرابط؛ الصور القديمة قد تبقى في ذاكرة منصات المشاركة حتى تحديثها.

## نتائج التحقق لهذه المراجعة

- اختبارات الإنتاج تضرب عامل HTTP متحكمًا فيه باستخدام `httpx.MockTransport` مع إعداد proxy للإنتاج؛ هي اختبارات عقد البروتوكول، **وليست استدلال GPU**.
- اختبار مستقل بثمانية اتصالات SQLite متوازية أثبت نجاح حجز واحد فقط عند عدم كفاية الرصيد لاثنين، ثم تحرير الرصيد مرة واحدة.
- اختبارات ترحيل قاعدة البيانات من البداية وإلى الخلف ثم للأمام ضمن مجموعة الوحدات نجحت.
- اختبار JavaScript أثبت استخدام أرقام usage الفعلية في Playground، ورفض خطأ SSE أو stream دون نهاية واستهلاك مؤكدين.
- فحص المتصفح للصفحة الرئيسية ودليل المطور وسياسة الاسترداد على desktop و390px mobile: لا أخطاء JavaScript ولا overflow أفقي. تم فحص صور الصفحات وصورة المشاركة.
- فحص Ruff للملفات المعدلة وJavaScript syntax و`git diff --check` نجح. تم التحقق من صياغة Compose بمتغيرات اختبار؛ لم يتم بناء صورة Docker أو تشغيلها ولم يتم اختبار PostgreSQL أو GPU فعلي.
- فحص المصدر المنشور أكد عدم وجود Open Graph/Twitter image وقت المراجعة؛ تغيير الصورة الجديد لم ينشر بعد.

آخر نتيجة كاملة: **251 passed in 14.22s** للأمر `python -m pytest tests/unit tests/integration -q --tb=short`. يشمل ذلك **19 اختبار عقد إنتاج**؛ لا تساوي هذه النتيجة اختبار بيئة إنتاج فعلية.
