# خطة إعادة هيكلة منصة SpeedInfer الداخلية

التاريخ: 27 سبتمبر 2026 — الحالة: بدأ التنفيذ بعد اعتماد المستخدم؛ تفاصيل التسليم في `docs/WORKSPACE_IMPLEMENTATION_AR.md`.

توضيح معتمد: SpeedInfer خدمة مُدارة لتشغيل وتدريب النماذج وإتاحتها عبر API، وليست خدمة تأجير سيرفرات للمستخدم. أسعار الساعة تصف موارد تشغيل النموذج المُدار. أضيفت Buckets خاصة مع رفع حقيقي محدود للملفات واختيار مستقل للبيانات والأوزان داخل معالج التدريب والنشر.

## 1. النتيجة المطلوبة وحدود هذه الخطة

تحويل لوحة الاستخدام الحالية إلى منصة منظمة لإدارة دورة حياة النموذج: مشروع ← بيانات ← تدريب ← تقييم ← إصدار نموذج ← نشر ← مراقبة وتكلفة. تشمل التجربة صفحات مستقلة وروابط مباشرة، وتصميمًا متسقًا، وفصلًا واضحًا بين العمليات الحقيقية والمحاكاة والخدمات القادمة.

هذه الوثيقة تحدد التعديلات المقترحة ومعايير قبولها؛ إنشاء الملف لا يعني تنفيذها. مراجعة الوضع الحالي مبنية على الملفات المحلية، وليست تدقيقًا بصريًا للموقع المنشور أو إثباتًا لتشغيل GPU أو الدفع في الإنتاج.

هدف الإصدار الأول: منصة عرض تفاعلية متماسكة يمكن اختبار رحلاتها كاملة، مع المحافظة على الوظائف الموجودة، وإعداد حدود واضحة لإضافة مزود GPU أو API لاحقًا. هدف NVIDIA Inception مرتبط بالأهلية وقيمة المنتج الحقيقية، وليس بعدد الصفحات.

## 2. ما أثبتته مراجعة المشروع

| الجزء | الموجود حاليًا | الفجوة والتعديل المقترح |
|---|---|---|
| إنشاء الحساب والمفاتيح | `app.js` يرسل `create_api_key: true` عند التسجيل ويعرض المفتاح مباشرة؛ `api.js` يجعله افتراضيًا أيضًا | إلغاء الإنشاء التلقائي عبر الواجهة والعقد الخلفي، وجعل الإنشاء فعلًا صريحًا |
| تسجيل الدخول | مسار تسجيل الدخول يرجع `api_key=None` | لا دليل في هذا المسار على إنشاء مفتاح جديد عند كل دخول؛ نختبر إعادة الدخول والتحديث والنوافذ القديمة لتحديد أي سلوك إضافي |
| حفظ الأسرار | JWT في `localStorage` ومفتاح API الخام في `sessionStorage` | فصل جلسة الحساب عن مفاتيح الاستخدام؛ تقليل حفظ المفتاح الخام وإزالته من العرض والذاكرة عند الإغلاق والخروج |
| صفحات الحساب | Overview، Playground، API keys، Models، Usage & credits، Help، وصندوق فريق للمسؤول | إضافة أقسام المشاريع والتدريب والبيانات والنشر والمراقبة والإعدادات والسياسات |
| التسعير | باقات رصيد مسبق الدفع واحتساب توكنات | لا توجد منظومة اشتراكات شهرية أو أسعار GPU بالساعة في الكود الذي تمت مراجعته |
| التدريب | مسار Python لـSFT مع LoRA/QLoRA، تتبع MLflow وتقييم وتصدير، ومسار dry-run | لا توجد واجهات API لإدارة وظائف تدريب سحابية في قائمة المسارات المسجلة؛ نحتاج إدارة وظائف وعامل تنفيذ |
| المحاكاة الحالية للتدريب | `train.py` يولد مقاييس ثابتة وملف أوزان placeholder في مسار المحاكاة، ويختاره أيضًا عند غياب `CUDA_VISIBLE_DEVICES` | منع تسجيل هذه النتائج كأوزان صالحة أو قياسات أداء حقيقية؛ تحديد وضع التنفيذ صراحة والتحقق الفعلي من توافر GPU |
| النشر | بوابة استدلال وسجل نماذج وتكامل vLLM | لا توجد إدارة استئجار سيرفرات أو تشغيل/إيقاف موارد بالساعة |
| السياسات | نافذة بيانات تركز على طلبات التواصل مع وصف مختصر للحساب والاستخدام | صفحات سياسات كاملة مرتبطة بالسلوك الفعلي للمنتج |

مراجع التنفيذ: `speedinfer/frontend/js/{app,api,store}.js`، `speedinfer/frontend/index.html`، `speedinfer/gateway/routes/{auth,keys,billing,models}.py`، `speedinfer/gateway/app.py`، `speedinfer/config.py`، `speedinfer/training/{train,config}.py`.

## 3. أولوية أولى: إصلاح تجربة المفتاح والدخول

1. الحساب الجديد يدخل إلى صفحة ترحيب منظمة، بعدد مفاتيح صفر، دون نافذة أسرار أو إنشاء موارد تلقائيًا.
2. ضبط طلب التسجيل وافتراضات العميل والخادم على عدم إنشاء API key؛ مراجعة مخطط الطلب والاختبارات المرتبطة قبل تغيير العقد.
3. صفحة API Keys تعرض حالة فارغة وزر «إنشاء مفتاح». النموذج يطلب الاسم، النطاقات، وحدود الاستخدام والانتهاء بحسب صلاحيات الحساب.
4. يعرض السر مرة واحدة بعد إنشاء ناجح صريح، مع نسخ وتنبيه لحفظه؛ قوائم المفاتيح تعرض prefix وحالة وتواريخ فقط.
5. تنظيف محتوى نافذة السر عند إغلاقها وعدم إعادة فتحها بالتحديث أو التنقل. عدم وضع الأسرار في الروابط أو السجلات أو الإشعارات.
6. لا تعرض الواجهة JWT بوصفه مفتاح API؛ جلسة الحساب تسمح بالتنقل في المنصة دون امتلاك مفتاح استدلال.
7. Playground يشرح الحاجة إلى مفتاح بشكل اختياري وواضح. في المرحلة الانتقالية يُدخل المستخدم المفتاح للاستخدام المؤقت في الذاكرة؛ أي تشغيل بالجلسة وحدها يحتاج مسارًا خلفيًا مستقلًا محدود الصلاحيات.
8. مراجعة نقل جلسة الحساب إلى cookie آمنة `HttpOnly` و`Secure` مع ضوابط CSRF كجزء مستقل من تقوية المصادقة، بعد حصر تأثيره على العملاء الحاليين.

**اعتماد مهم:** الرصيد الحالي مرتبط بالمفاتيح في الدفع. المفتاح المنشأ يدويًا يبدأ بصفر عند غياب رصيد محدد؛ لذلك تعطيل الإنشاء التلقائي وحده لا يكفي. نحتاج سياسة منح الرصيد التجريبي مرة واحدة من الخادم، وعدم نسخه إلى كل مفتاح. المقترح النهائي محفظة على مستوى مساحة العمل مع حدود للمفاتيح، وترحيل الأرصدة بسجل تسوية يمنع التكرار. إلى حين ذلك تعرض الواجهة رصيد الحساب ورصيد المفتاح المتاح للاستهلاك بوضوح، ولا تعد برصيد قابل للاستهلاك غير موجود.

**القبول:** التسجيل، الدخول المتكرر، تحديث الصفحة، انتهاء الجلسة والخروج لا تُنشئ مفاتيح؛ إنشاء صريح واحد يُنتج مفتاحًا واحدًا؛ إعادة الطلب لا تكرر منح الرصيد؛ ولا تتسرب بيانات حساب سابق عند تبديل الحساب.

## 5. اتجاه التصميم وتجربة الاستخدام

- اعتماد Console هادئة: قائمة جانبية ثابتة قابلة للطي، عنوان واضح ومسار تنقل، محدد مشروع، مؤشر وضع المحاكاة، قائمة حساب. التفاصيل التسويقية تبقى في الموقع العام.
- نظام موحد للألوان والمسافات والخطوط والأزرار والبطاقات والجداول والنماذج والنوافذ والحالات؛ لون رئيسي واحد، وألوان حالة ثابتة.
- الصفحة تبدأ بعنوان ووصف قصير وإجراء رئيسي واحد، ثم المحتوى؛ عرض الأرقام المهمة فقط وإتاحة التفاصيل داخل المورد.
- الصفحات التشغيلية تستخدم جداول للفرز والتصفية والبحث والتقسيم، مع صفحة تفاصيل لكل مورد. بطاقات الأسعار متساوية البنية وتوضح وحدة الحساب بدل إبراز رقم معزول.
- توفير حالات التحميل والفراغ والفشل وإعادة المحاولة وغياب الصلاحية وانقطاع الخدمة؛ لا تُستبدل البيانات المفقودة بأرقام تجريبية غير موسومة.
- إظهار «محاكاة — لا توجد رسوم فعلية» أعلى مسارات التدريب والحوسبة التجريبية، وعلى السجلات والتقارير الناتجة منها.
- دعم الهاتف ولوحة المفاتيح والتركيز والتباين؛ تخطيط يدعم RTL، مع اتجاه LTR للأكواد والمفاتيح والأرقام المختلطة. الافتراض المقترح إصدار إنجليزي أساسي مع بنية ترجمة عربية منظمة.
- الروابط العميقة والتحديث وزرا الرجوع والتقدم تعمل دون فقد الصفحة. الحفاظ على تحويلات روابط الأقسام القديمة أثناء الانتقال.

## 6. صفحات التدريب وأنواعه

لا نخلط بين هدف التدريب وطريقته: SFT هدف ضبط بإشراف، وLoRA/QLoRA طريقتان لتحديث جزء من الأوزان. النموذج يسأل عن نوع المهمة أولًا ثم طريقة التدريب المتوافقة.

| المسار | الوضع المثبت من الكود | المعالجة في المنصة |
|---|---|---|
| SFT باستخدام LoRA | يوجد مسار تنفيذ محلي | أول مسار يُربط بإدارة الوظائف؛ محاكاة واضحة حتى تجهيز عامل GPU |
| SFT باستخدام QLoRA | يوجد إعداد 4-bit ومسار quantization | اختيار منفصل مع شرح الذاكرة والتحقق من التوافق |
| Full Fine-tuning | غير مثبت كمسار مستقل جاهز | صفحة تعريف وخيارات مخططة؛ تفعيل بعد تنفيذ العامل والتحقق |
| DPO / Preference tuning | غير موجود في المسارات المراجعة | مخطط لاحق مع صيغة بيانات chosen/rejected |
| Continued pretraining | غير موجود كخدمة | خارطة طريق مع متطلبات الموارد والتكلفة |
| Distillation | غير موجود كخدمة | خارطة طريق تتطلب نموذج معلم وبيانات وتقييم |
| تدريب متعدد GPU أو صور/صوت | غير مثبت | توسع لاحق، لا يُعلن دعم فعلي قبل تنفيذه |

معالج التدريب: اختيار المشروع والنموذج والترخيص ← نوع المهمة والطريقة ← dataset والتحقق من الصيغة ← تقسيم تدريب/تقييم ومنع تسرب البيانات ← إعدادات مبسطة ومتقدمة ← مورد وحد ميزانية ← ملخص السعر والوضع ← إنشاء الوظيفة.

تفاصيل الوظيفة: حالات `draft / validating / queued / running / succeeded / failed / cancelled`، إعدادات محفوظة، سجلات منزوعة الأسرار، تقدم، تكلفة تقديرية، ملفات ناتجة، وإمكانية إعادة التشغيل كوظيفة جديدة. التقييم يقارن إصدارين بنفس البيانات والإعدادات ويذكر مصدر المقاييس.

رفع البيانات يحتاج حدود حجم وصيغ، تحققًا من الملكية، تخزينًا معزولًا، روابط محدودة العمر، وحذفًا قابلًا للتتبع. أي رفع في العرض التجريبي يوضح إن كان الملف سيُحفظ؛ الأفضل بيانات أمثلة أولًا حتى تشغيل التخزين الحقيقي.

## 7. النشر على سيرفرات بالساعة

رحلة النشر: اختيار نموذج أو إصدار ناتج عن التدريب ← التحقق من ملاءمة الذاكرة والدقة ← نوع GPU وعدده والمنطقة المتاحة ← مساحة القرص ← عدد النسخ وحدود الميزانية والإيقاف التلقائي ← مراجعة السعر ← «إنشاء نشر تجريبي».

صفحة المورد تعرض مواصفاته ومصدر السعر ووقته، الحالة، الإصدار المنشور، زمن التشغيل، التكلفة التقديرية، السجلات، وزر الإيقاف. رابط النهاية في المحاكاة موسوم وغير معروض كنقطة استدلال حقيقية؛ أمثلة SDK تحتوي placeholders واضحة.

حالات النشر المقترحة: `draft / provisioning / running / stopping / stopped / failed / deleted`. الخادم يفرض الانتقالات الصحيحة وملكية المورد ويمنع تكرار الإنشاء. المحاكاة تحفظ الحالة عبر التحديث وإعادة الدخول، وتتيح سيناريو فشل أو إلغاء لاختبار التجربة.

يُحدد العقد لاحقًا متى يبدأ وينتهي احتساب الحوسبة، وهل التخزين يستمر بعد إيقاف GPU، ووحدة تقريب الزمن. في المحاكاة المقترحة تُحسب الحوسبة أثناء `running` فقط، بالثواني مع عرض سعر الساعة؛ وهذه قاعدة عرض تجريبي قابلة للتغيير وفق عقد المزود.

| الرصيد التجريبي | 10 دولارات افتراضيًا | `trial_credit_balance`؛ الإتاحة والسياسة يقررهما الخادم |
| الاشتراك الشهري | غير موجود | الدفع الحالي `one_time` لشحن الرصيد |
| GPU بالساعة | غير موجود | يلزم كتالوج خلفي جديد؛ لا يجوز نسب أرقام مقترحة إلى أسعار موجودة |

هذه قيم من النسخة المحلية والإعدادات المقروءة، وليست تحققًا من إعدادات موقع منشور أو جلسة تشغيل قد تحمل overrides أخرى. أثناء التنفيذ تُراجع استجابات الأسعار الفعلية ويُعتمد الخادم كمصدر واحد.

مثال وفق السعر الحالي: مليون توكن إدخال ومليون إخراج = 0.80 دولار. تُعرض معادلة الاستهلاك بوضوح، مع فصل مبالغ الشحن عن رسوم الاستهلاك.

### 8.2 كتالوج محاكاة مقترح للإضافة إلى الباك إند

الأرقام التالية افتراضات للعرض والاختبار فقط، ليست أسعار سوق أو عروض مزود أو أسعارًا حالية في المشروع. تُستخدم فئات عامة حتى تحديد السيرفرات أو API المتعاقد عليه؛ لا ندّعي توافر طراز GPU معين.

| فئة تجريبية | ذاكرة GPU افتراضية | سعر الساعة المقترح | 8 ساعات لمحاكاة واحدة |
|---|---|---|---|
| Demo Small | 24 GB | 0.50 دولار | 4.00 دولارات |
| Demo Medium | 48 GB | 1.00 دولار | 8.00 دولارات |
| Demo Large | 80 GB | 2.00 دولار | 16.00 دولارًا |

المواصفات والأسعار السابقة مدخلات محاكاة وليست ضمانًا لملاءمة نموذج بعينه. سعر التدريب التجريبي يتبع مورد التدريب المختار دون رسوم إضافية مفترضة. التخزين ونقل البيانات يظهران «غير مسعّرين في المحاكاة» ولا تُخترع لهما رسوم.

تضاف بيانات الأسعار إلى كتالوج خلفي يتضمن `sku`, `currency`, `unit`, `unit_price`, `mode`, `source`, `effective_at`, `version`, `availability`، وتقرأها كل البطاقات والحاسبات من API واحد. يعيد مسار تقدير التكلفة نسخة السعر والموارد والمدة؛ الخادم يعيد التحقق عند إنشاء المورد.

التقدير = سعر المورد بالساعة × ساعات التشغيل × عدد النسخ. إذا كان SKU يمثل سيرفرًا بعدة GPUs فلا يُضرب في عدد GPU مرة أخرى. يظهر أن التقدير لا يشمل البنود غير المسعرة. تغيير السعر لا يعدّل سجل تكلفة قديمًا بأثر رجعي.

صفحة التسعير تضم أقسام «استهلاك API»، «حوسبة بالساعة»، «تدريب»، «حلول مخصصة». صفحة الفوترة تضم المحفظة والمعاملات والشحن؛ لا تستخدم تسمية اشتراك شهري لشراء رصيد. الاشتراكات الدورية اختيار مستقبلي يحتاج منتجات وتجديدًا وإلغاءً واستحقاقات ومعالجة دفع مستقلة.

## 9. حدود المحاكاة والاتصال بالمزود لاحقًا

- وضع التشغيل يُفرض من الخادم، مع `is_simulated` على الوظائف والموارد والنتائج وسجلات التكلفة. لا يكفي تغيير زر في المتصفح.
- فصل رصيد وتكلفة المحاكاة عن الأموال الفعلية. لا checkout ولا خصم ولا فاتورة مدفوعة نتيجة مورد تجريبي.
- طبقة `ComputeProvider` و`TrainingExecutor` تضم تنفيذ محاكاة أولًا، ثم موصل المزود الحقيقي. اختيار المزود قرار مؤجل حتى توافر الأسعار والعقد والسعة.
- المحاكاة لا تتصل بمزود مدفوع، ولا تنتج benchmark حقيقيًا، ولا تسمح بترقية placeholder إلى نموذج إنتاجي.
- تشغيل حقيقي يحتاج مفاتيح مزود محفوظة في الخادم، فحص سعة وتوافق، عزل مستخدمين، حدود إنفاق، إيقاف موارد موثوقًا، معالجة فشل وتسوية تكلفة، واختبارًا على مورد فعلي.
- إذا كان المزود API للاستدلال فقط، لا تُعرض إدارته كتأجير GPU مملوك للمستخدم؛ قدرات الواجهة تتبع نوع الخدمة الفعلي.

صفحات عامة كاملة بروابط من التسجيل والفوتر والدفع والكونسول، مع تاريخ سريان وإصدار ووسيلة تواصل. المطلوب كتابة محتوى خاص بسلوك SpeedInfer وبلد الشركة ومزوديها؛ البيانات التجارية غير المؤكدة تبقى عناصر للمراجعة، ولا تُنشر كنص نهائي مختلق.

| `/legal/privacy` | بيانات الحساب والدفع والاستخدام والمحتوى، أغراض المعالجة، الجهات المستلمة، الاحتفاظ والحذف والتواصل |

## 11. العمل الخلفي المطلوب كي تعمل الصفحات

الإبقاء على FastAPI ومسارات الاستدلال المتوافقة حاليًا، وتقسيم الواجهة إلى وحدات صفحات ومكونات مشتركة بدل تضخيم `index.html` و`app.js`. قرار استخدام إطار واجهة جديد يُحسم في مرحلة الأساس وفق تكلفة النقل؛ ليس شرطًا لهذه الخطة.

الكيانات الجديدة: Workspace، Project، Dataset/Version، TrainingJob، EvaluationRun، ModelArtifact، Deployment، ComputeInstance، PriceSKU/Version، CostEstimate، UsageEvent، Wallet/Ledger، AuditEvent، PolicyAcceptance. كل مورد له مالك ومساحة عمل ووضع تشغيل وتواريخ واضحة.

عقود API المقترحة:

- `/v1/projects` و`/v1/datasets`: إدارة موارد المشروع وعمليات التحقق والرفع.
- `/v1/training/jobs` و`/:id/cancel` و`/:id/logs`: إنشاء وظائف ومتابعتها؛ عامل خلفي بدل تنفيذ التدريب داخل طلب HTTP طويل.
- `/v1/evaluations` و`/v1/artifacts`: نتائج وإصدارات مع مصدرها وحالتها الحقيقية أو المحاكية.
- `/v1/deployments` و`/v1/compute/instances`: دورة حياة النشر والموارد.
- `/v1/pricing/catalog` و`/v1/pricing/estimate`: كتالوج موحد وتقدير من الخادم.
- `/v1/workspace/usage` و`/v1/billing/transactions`: بيانات كونسول مصادق عليها بجلسة الحساب، دون إجبار المستخدم على مفتاح خام.
- `/v1/policies` و`/v1/policy-acceptances`: الإصدارات والموافقات.

كل عملية تُراجع ملكية المورد وصلاحياته؛ الإنشاء والدفع ومنح الرصيد يحتاج منع التكرار. نقل المحفظة يحتاج ترحيلًا قابلًا للمراجعة وتسوية تحفظ الأرصدة، مع منع خصم التوكنات والحوسبة لنفس البند مرتين. موصل Whop الحالي يظل مسار شحن مستقلًا إلى أن يُراجع الربط الجديد.

## 12. NVIDIA Inception: الأهلية أولًا

وفق [الصفحة الرسمية للبرنامج](https://www.nvidia.com/en-us/startups/) التي تمت مراجعتها بتاريخ هذه الخطة: يلزم وجود شركة مسجلة، عمرها أقل من عشر سنوات، مطور واحد على الأقل، وموقع يعمل. لا يشترط وجود إيرادات أو استخدام منتجات NVIDIA مسبقًا. تطلب عملية التقديم عرضًا يوضح الشركة وحلها وقيمتها.

**نقطة حاسمة:** الصفحة الرسمية تستثني مقدمي الخدمات السحابية، وبائعي إعادة البيع والتوزيع، إلى جانب الاستشارات والتطوير الخارجي والشركات المرتبطة بالعملات المشفرة والشركات العامة. لذلك نموذج عمل قائم على بيع ساعات GPU وحده قد يتعارض مباشرة مع الهدف. وجود واجهة سحابية لا يحسم التصنيف؛ طبيعة النشاط الفعلية هي موضع التحقق.

تحديث البحث بعد توضيح نشاط الشركة: لا يصح تعميم الاستبعاد على منصات تشغيل وتدريب النماذج المُدارة. توجد سوابق رسمية قريبة، منها [Baseten](https://www.nvidia.com/en-us/case-studies/baseten/)، و[Fireworks ضمن أعضاء Inception في NeurIPS 2023](https://www.nvidia.com/en-eu/events/neurips/)، و[Anyscale](https://blogs.nvidia.com/blog/microservices-ai-enterprise/). هذه سوابق وليست ضمانًا للقبول الحالي. التصميم يعرض قيمة المنتج ووظائفه الحقيقية، ولا يستخدم شعار NVIDIA أو يوحي بعضوية غير معتمدة.

المقترح: تطوير قيمة برمجية حقيقية يمكن إثباتها في إدارة دورة حياة النموذج، القياس، التقييم، وتحسين التشغيل، وتوصيف المنتج كما يعمل فعلًا. لا نعيد تسمية إعادة البيع للتحايل على الأهلية. إذا ظل النشاط الأساسي تقديم حوسبة سحابية، يطلب المؤسس توضيح الأهلية من فريق البرنامج قبل الاستثمار في التقديم على هذا الأساس؛ لم تُرسل أي مراسلة ضمن هذه المهمة.

حزمة الجاهزية المقترحة:

1. بيانات التسجيل وتاريخ الشركة والفريق ووسائل تواصل حقيقية؛ لا يمكن إثباتها من المستودع.
2. موقع عام متسق يشرح المنتج والعملاء المستهدفين والأسعار وحالة الإتاحة والسياسات.
3. عرض تقديمي يوضح المشكلة والحل والميزة البرمجية ونموذج العمل والسوق وخارطة الطريق.
4. Demo لمسار بيانات ← تدريب تجريبي ← تقييم تجريبي ← نشر تجريبي، مع وسم صريح؛ وعرض منفصل لأي مسار يعمل فعلًا.
5. نتائج أداء قابلة لإعادة القياس عند توفر GPU، مع العتاد والإعدادات والتاريخ؛ نتائج المحاكاة ليست دليل أداء.
6. وصف تقنيات NVIDIA المستخدمة فعلًا وخطة التقنيات المستقبلية، دون شارة عضوية أو شراكة قبل اعتمادها.

هذه خطوات تحسين جاهزية، ولا تضمن القبول. الدليل المحلي `NVIDIA_INCEPTION_MASTER_GUIDE.md` ليس مرجعًا ملزمًا؛ تُراجع ادعاءاته مقابل المصدر الرسمي قبل استخدامها.

## 14. معايير القبول النهائية

- [ ] التسجيل والدخول لا ينشئان API key، ولا تظهر نافذة مفتاح دون طلب المستخدم.
- [ ] الرصيد التجريبي لا يتكرر، ورصيد المفتاح/المحفظة المعروض مطابق لما يمكن استهلاكه.
- [ ] كل صفحة أساسية لها رابط مباشر يعمل بعد التحديث، وحالات تحميل وفراغ وفشل وصلاحية.
- [ ] مستخدم لا يقرأ بيانات أو وظائف أو ملفات مستخدم آخر عبر تغيير المعرّف في الطلب.
- [ ] الأسعار تأتي من الباك إند، مع العملة والوحدة ونسخة السعر وحالة المحاكاة.
- [ ] تعديل أسعار الكتالوج ينعكس على تقدير جديد ويحافظ على السجلات القديمة.
- [ ] لا تُخلط باقات الشحن باشتراكات شهرية ولا تُخلط تكلفة API بتكلفة GPU.
- [ ] التدريب والنشر التجريبيان قابلان للإنشاء والتتبع والفشل والإلغاء دون رسوم حقيقية.
- [ ] نتائج وأوزان المحاكاة لا تُقبل في نشر حقيقي ولا تُعرض كدليل أداء.
- [ ] احتساب الساعة يطابق حالات المورد والمدة والنسخ، ويتوقف وفق القاعدة المعلنة.
- [ ] السياسات كاملة ومتاحة علنًا، مع إصدارات وموافقة وبيانات شركة معتمدة قبل النشر النهائي.
- [ ] التنقل والجداول والنماذج تعمل على الهاتف ولوحة المفاتيح دون تمرير أفقي غير مقصود.
- [ ] نجاح اختبار رحلة حساب جديد، ومستخدم عائد، وحساب بلا مفتاح، وحساب بلا رصيد، وحساب مسؤول.
- [ ] تُراجع الاختبارات الحالية للمصادقة والمفاتيح والفوترة والتدريب ومسارات الواجهة، وتضاف اختبارات للعزل والمحاكاة والتكلفة والانتقالات حسب المخاطر.
- [ ] تتطابق صفحة المنتج والعرض التقديمي وحالة الميزات، ويُحسم تعارض نموذج العمل مع أهلية Inception قبل تقديم ادعاء بالجاهزية.

## 15. قرارات المراجعة المطلوبة

المقترح المبدئي: اعتماد المراحل 1–3 كأولوية لواجهة شبه متكاملة، واستخدام الإنجليزية مع تجهيز التعريب، والإبقاء على الدفع الحالي شحن رصيد، واعتماد فئات GPU التجريبية العامة إلى حين اختيار المورد. تُراجع هذه الاختيارات مع المؤسس قبل التنفيذ.

قرارات لا يمكن اختلاقها: اسم الكيان القانوني وبلده، مدد الاحتفاظ والاسترداد التجارية، مزود الموارد وأسعاره الفعلية، هل النشاط الأساسي منتج برمجي أم خدمة سحابية، ومن يملك مسؤولية التشغيل والدعم. هذه لا تمنع إعداد التصميم والمحاكاة، لكنها شروط لإتمام السياسات والبيع والتقديم بصورة صحيحة.
